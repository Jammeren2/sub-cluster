# Возврат переключения домена через REG.RU

Система из коммитов `97d5055`, `c6caaec` и `9b84ce2` осталась в проекте.
Переход на PostgreSQL (`e39d2e3`) отключил обмен копиями БД, но не DNS-фейловер.
Для двух узлов прежнее требование большинства не позволяет одному оставшемуся
перехватить домен. Две постоянные A-записи также не гарантируют повторный запрос
Happ на другой адрес после HTTP 503.

## Что делает текущая версия

- Сохраняет приоритеты, ручной выбор активного узла и историю переключений.
- Проверяет `/healthz` домена подписок непосредственно на IP каждого узла,
  сохраняя Host, SNI и проверку сертификата. Проверка не зависит от общего DNS.
- После заданного числа ошибок исключает узел из кандидатов. Не публикует свой
  IP, если собственная выдача подписок недоступна. Peer API также должен работать.
- Добавляет новый A-адрес и подтверждает его через API **до** удаления старых.
  Удаляет только конкретные лишние A-адреса указанного поддомена. TXT для ACME,
  AAAA и другие поддомены не меняет. Ошибки чтения/удаления не считаются успехом.
- Активный узел сверяет A-записи каждые пять минут, исправляя лишний второй IP.
  Админские домены должны оставаться статичными и отдельными для каждого узла.

## Включение на существующем кластере

1. Развернуть одинаковую новую версию приложения на обоих серверах.
2. В настройках домена `happ.wschat.ru`: зона `wschat.ru`, поддомен `happ`,
   публичный адрес `https://happ.wschat.ru`, действующие реквизиты REG.RU.
   Реквизиты в прокси Traefik для сертификатов сами по себе не настраивают приложение.
   API должен разрешать оба исходящих публичных IP серверов.
3. На работающем основном узле, **внутри контейнера приложения** с его штатным
   окружением и доступом к общей БД, сначала просмотреть план:

   ```sh
   python configure_dns_failover.py --domain happ.wschat.ru --two-node
   ```

   Если пароль домена ещё не сохранён, передать `REGRU_USERNAME` и `REGRU_PASSWORD`
   через секретное окружение этого запуска. `SECRET_KEY` должен быть настроен.
   Скрипт не печатает пароль. Не передавать пароль аргументом командной строки.

4. Применить настройки и оставить один адрес работающего узла в DNS:

   ```sh
   python configure_dns_failover.py --domain happ.wschat.ru --two-node --apply --activate-here
   ```

   Это включает общий механизм фейловера для включённых доменов подписок,
   выключает требование большинства **только по явному флагу** `--two-node`,
   убирает ручное закрепление и отключает автоматический возврат на основной узел.
   Порог — 3 ошибки, опрос — 10 секунд, пауза между переключениями — 60 секунд.
   Фактическое обнаружение может быть дольше из-за сетевых таймаутов.
   В общей PostgreSQL настройки видны обоим узлам. Для legacy SQLite нужно
   дождаться синхронизации до аварийного теста.
5. Проверить через API и авторитетные NS, что остался один A-адрес. Проверить TTL
   у REG.RU: по последним внешним проверкам он был 3600 секунд. Уменьшение TTL
   не очищает старые кэши; не обещать переключение за 30 секунд. Не менять TTL
   всей зоны вслепую, поскольку в ней есть другие сервисы.

## Проверка отказа

Сначала остановить только приложение активного узла, сохранив PostgreSQL и прокси.
На оставшемся узле должна появиться успешная запись `auto` в истории, а A-запись
должна смениться на его IP. Проверить подписку через этот IP с Host/SNI
`happ.wschat.ru`; затем — через обычный DNS после истечения кэша. Восстановить
приложение и убедиться, что при выключенном failback DNS не скачет обратно.
Проверка личной ссылки должна использовать её текущий HWID; диагностический HEAD
не привязывает новое устройство и не записывает статистику.

Полный отказ машины тестировать отдельно. DNS-фейловер **не повышает standby
PostgreSQL до primary**, не создаёт writable endpoint и не снимает синхронное
ожидание отключившейся реплики. При недоступности общей БД оставшееся приложение
может перестать выдавать подписки и менять настройки/DNS. Не отключать гарантии
БД и не повышать реплику автоматически без защиты от двух primary.

Без кворума DNS-переключение при сетевом разделении может вызывать конкуренцию
узлов; это осознанное ограничение двух серверов, а не гарантия полной HA.
Сертификаты нужны на обоих узлах заранее, DNS-01 REG.RU для них сохраняется.
