# Общая PostgreSQL для всех серверов

Этот режим заменяет раздельные SQLite единой PostgreSQL. Все серверы используют
**одинаковый DATABASE_URL на writable endpoint primary**. Изменения видны другим
серверам после COMMIT, без периодической синхронизации копий. Это сетевая операция,
а не буквальные «ноль миллисекунд».

В общей БД находятся граф, настройки, участники, блокировки, статистика с именами
и контактами, личные ссылки, привязки HWID, лимиты, сессии панели и результаты
проверок. Очереди проверок разделены по NODE_ID в отдельных схемах той же БД:
каждый сервер проверяет доступность из своей сети. Успешные результаты объединены
сразу после записи. Неудача одного узла не отменяет успех другого. Процессы VPN,
временные файлы, сетевые кеши и наблюдения за доступностью узлов остаются локальными.

Личные ссылки обслуживаются любым узлом: старый `personal_owner` больше не
перенаправляет запросы. Создание ссылки и привязка HWID защищены транзакциями.
Статистика не суммируется повторно через peer API. Старые механизмы LWW и обмена
результатами отключены в режиме PostgreSQL. REG.RU и DNS-фейловер в этом коммите
сохранены: их удаление и смена DNS — следующий отдельный этап.

## Требования к сервису БД

- PostgreSQL 17 или совместимая более новая версия; отдельная БД и пользователь
  приложения с правом создавать таблицы, индексы и схемы внутри этой БД.
- Primary + **синхронный** standby, автоматическое переключение с fencing старого
  primary и стабильным writable endpoint. Клиенты приложения не подключаются
  напрямую к standby/read-only endpoint. При асинхронном standby подтверждённая
  привязка устройства может потеряться при аварии — это не эквивалентный режим.
- У провайдера необходимо включить гарантию сохранения подтверждённых транзакций
  при failover и проверить её. Одна строка DATABASE_URL не создаёт standby,
  кворум или автоматическое переключение. Сервис пока нужно создать отдельно.
- Приватная сеть либо TLS с проверкой сертификата (`sslmode=verify-full` и CA),
  доступ только с серверов приложения. У всех узлов одинаковые `CLUSTER_SECRET`,
  `SECRET_KEY`, админские реквизиты и настройки Turnstile; уникальный `NODE_ID`.
- Резервные копии/PITR отдельно от реплики. Отказ всей БД временно делает сервис
  недоступным; приложение не переключается на устаревшую SQLite и не создаёт
  вторую независимую привязку HWID. `/healthz` возвращает 503 при отказе БД.

Пример переменной (замените placeholders; пароль задаётся через секреты Coolify):

```dotenv
DATABASE_URL=postgresql://APP_USER:URL_ENCODED_PASSWORD@WRITABLE_ENDPOINT:5432/subcluster?sslmode=verify-full
```

Не используйте два независимых PostgreSQL primary и не копируйте файлы SQLite
между работающими серверами. Для production нужен один согласованный writable
endpoint. Приложение использует READ COMMITTED и транзакционные advisory locks;
после переподключения соединения читают актуальное состояние.
См. [транзакционные блокировки PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html)
и [транзакции Psycopg](https://www.psycopg.org/psycopg3/docs/basic/transactions.html). Неопределённый исход
записи при сетевом разрыве не приводит к автоматическому повторению счётчика.

## Перенос существующих данных

Перенос выполняется один раз, в окно обслуживания, **до запуска приложений с
DATABASE_URL**. Старые и новые узлы не должны одновременно принимать записи.

1. Создайте сервис БД и резервную копию каждого существующего узла. Выберите узел,
   чей граф/настройки станут основными. Запишите исходный NODE_ID каждой копии.
2. Остановите приложения на всех узлах. Получите консистентные SQLite snapshots:
   SQLite backup API / `.backup`, либо копию после корректного закрытия БД.
   Простое копирование живого `cluster.db` без WAL может потерять записи.
3. Установите зависимости нового коммита. Задайте DATABASE_URL в окружении процесса
   миграции. Сначала проверьте состав каждого snapshot без изменений в БД:

   ```sh
   python migrate_shared_db.py --sqlite /backups/node1.db --node node1 --dry-run
   python migrate_shared_db.py --sqlite /backups/node2.db --node node2 --dry-run
   ```

4. Импортируйте основной snapshot, затем каждый оставшийся. `--authoritative-config`
   используется **ровно один раз**. Имена ниже замените исходными NODE_ID:

   ```sh
   python migrate_shared_db.py --sqlite /backups/node1.db --node node1 --authoritative-config
   python migrate_shared_db.py --sqlite /backups/node2.db --node node2
   ```

   Граф/настройки/failover берутся с основного узла; участники объединяются.
   Личные ссылки, контакты, HWID, лимиты, статистика и собственные результаты
   проверок импортируются со всех узлов. Чужие копии проверок не импортируются
   повторно. Несовместимые личные ссылки прерывают весь импорт данного snapshot.
   Повтор того же импорта безопасен; другая копия уже импортированного NODE_ID
   отклоняется, чтобы не удваивать счётчики. `--dry-run` показывает только состав
   snapshot, а не проверку всех конфликтов в целевой БД.

5. Задайте одинаковый DATABASE_URL **на всех** приложениях, сохранив NODE_ID.
   Пересоберите/запустите одинаковый коммит. Не запускайте старые контейнеры
   с SQLite после переноса. DB_FILE остаётся только для legacy-режима и резервной
   копии; при наличии DATABASE_URL он не используется для чтения/записи состояния.
6. Проверьте `/healthz` каждого узла. Изменение графа на одном должно немедленно
   читаться на другом. Личная ссылка с тем же HWID должна работать через оба узла,
   с другим HWID — отклоняться. Проверьте число подписок, контакты и статистику.
7. Отдельно протестируйте переключение PostgreSQL primary→standby, сохранность
   привязки устройства и переподключение приложений. Только после этого меняйте
   DNS и удаляйте интеграцию REG.RU следующим коммитом.

Старые сессии панели были в памяти и потребуют повторного входа. Новые сессии
хранятся в общей БД. После начала записи в PostgreSQL откат на старые SQLite-копии
потеряет новые изменения; откатывать следует приложение с сохранением общей БД.

## Проверка разработчиком

`shared_db_test.py` работает только при явно заданном TEST_DATABASE_URL и удаляет
тестовые данные. Используйте **отдельную одноразовую БД**, никогда production:

```sh
TEST_DATABASE_URL=postgresql://.../disposable_db python shared_db_test.py
```

Также остаются `selftest.py`, `personal_test.py`, `source_checks_test.py` для
legacy-режима (запускайте без DATABASE_URL).
