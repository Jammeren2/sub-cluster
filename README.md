# sub-cluster

Самохостящийся **кластер VPN-подписок** на чистом Python: несколько узлов отдают
ссылки-подписки, синхронизируют конфиг между собой и переживают падение любого
сервера за счёт **DNS-фейловера через API reg.ru**. Есть веб-панель с графовым
редактором подписок, маршрутизацией трафика по приложениям (geosite/geoip) и
диагностикой обхода DPI (zapret).

- **Без зависимостей** — только стандартная библиотека Python 3 (http.server, sqlite3, ssl).
- **Отказоустойчивость** — узлы пингуют друг друга, при падении активного самый живой по
  приоритету перепривязывает A-запись домена подписок на себя (кворум против split-brain).
- **Мультидомен / мультитенант** — несколько доменов подписок, у каждого свой аккаунт
  reg.ru и порядок приоритета узлов; маршрут host-aware (доступен на своём домене).
- **Графовый редактор** — источники → ноды (группа-страна, авто-выбор, роутер) → маршруты.
- **Синк конфига** — SQLite на каждом узле; конфиг — last-writer-wins, список узлов — CRDT;
  секреты шифруются (`SECRET_KEY`), peer-API подписан HMAC (`CLUSTER_SECRET`).

> ⚠️ Не размещай в публичном доступе панель без сильного `ADMIN_PASSWORD` и уникальных
> `SECRET_KEY`/`CLUSTER_SECRET` (см. [Безопасность](#безопасность)). Сам код секретов не
> содержит — все домены/IP/токены задаются через окружение и панель.

## Архитектура

```
  admin.example.net→узел1   admin2.example.net→узел2   admin3…→узел3  (статичные)
            ▼                          ▼                        ▼
        reverse-proxy:443         reverse-proxy:443        reverse-proxy:443
   ┌──────── узел 1 ───────┐  ┌──────── узел 2 ───────┐  ┌──────── узел 3 ───────┐
   │ ADMIN :8080  SUB :8081│  │ ADMIN :8080  SUB :8081│  │ ADMIN :8080  SUB :8081│
   └───────────┬───────────┘  └───────────┬───────────┘  └───────────┬───────────┘
               └── peer-API (HMAC) через admin-домены по 443: живость + синк ──┘
                         (SQLite на каждом; config — LWW, members — CRDT)
        happ.example.com ──reg.ru API──► A-запись на активный (самый живой по приоритету)
```

Ключевая идея: узлы ходят друг к другу через **статичные admin-домены по 443**
(их и так держит reverse-proxy), поэтому **отдельные порты кластера наружу
открывать/пробрасывать не нужно** — снимает проблемы с NAT и фаерволами.
Фейловерятся только домены подписок (каждый — на свой активный узел).

**Домены:**
- **admin-домен у каждого узла свой и статичный** (`admin.example.net`,
  `admin2.example.net`, …) — панель узла всегда доступна, A-записи прописываешь вручную,
  reg.ru их не трогает. Через эти же домены (по 443) узлы общаются между собой.
- **домены подписок** для клиентов (`happ.example.com` и др.) — **фейловерятся**: reg.ru
  переключает A-запись каждого на его активный узел. Доменов может быть несколько, у
  каждого свой аккаунт reg.ru и (опц.) свой порядок приоритета узлов.

**Порты на узле:** `ADMIN_PORT` (8080, панель + peer-API), `SUB_PORT` (8081, подписки),
`CLUSTER_PORT` (8083, необязательный прямой peer-API по IP — фолбэк).

## Быстрый старт (локально)

```bash
git clone <репозиторий> sub-cluster && cd sub-cluster
cp .env.example .env          # задай секреты и параметры узла
python3 sub_server.py         # запустит admin :8080 и sub :8081
python3 selftest.py           # 266 проверок, без сети и зависимостей
```

Зависимостей нет — нужен только Python 3. Для прод-деплоя см. ниже.

## Переменные окружения (на каждом узле)

| Переменная        | Назначение                                                         |
|-------------------|--------------------------------------------------------------------|
| `NODE_ID`         | Уникальный **постоянный** id узла (не меняй между деплоями!)        |
| `NODE_LABEL`      | Человеческая метка (видна в панели)                                 |
| `NODE_PUBLIC_IP`  | Публичный IP сервера — он прописывается в DNS **подписок** при фейловере |
| `NODE_PRIORITY`   | Приоритет (**меньше = важнее**). Активным становится самый живой с наименьшим |
| `CLUSTER_URL`     | **Свой admin-домен** этого узла (`https://admin2.example.net`) — адрес для пиров |
| `ADMIN_DOMAIN`    | Для Caddy (standalone): admin-домен узла (домены подписок задаются в панели — Caddy ловит их catch-all-блоком) |
| `PEERS`           | admin-домены **других** узлов через запятую (бутстрап; дальше синк сам) |
| `CLUSTER_SECRET`  | Секрет подписи peer-запросов — **одинаковый на всех узлах**         |
| `SECRET_KEY`      | Ключ шифрования секретов в БД — **одинаковый на всех узлах**        |
| `ADMIN_USER` / `ADMIN_PASSWORD` | Доступ в панель (дефолтный/пустой пароль → отказ старта) |
| `DB_FILE`         | Путь к SQLite (в Docker — `/data/cluster.db`, volume)              |
| `CACHE_TTL`       | Кэш upstream, минимум 10800 сек (3 часа); одновременные запросы объединяются в один |

reg.ru-логин/пароль и домены подписок задаются в панели (`/settings`) **один раз** и
расходятся по кластеру (пароли шифруются `SECRET_KEY`, поэтому ключ должен совпадать на
всех узлах). У каждого домена — свой аккаунт reg.ru.

## Деплой

Два compose-файла: `docker-compose.yml` — для Coolify (только приложение, HTTPS делает
прокси Coolify); `docker-compose.standalone.yml` — для серверов без Coolify (приложение + Caddy).

### DNS-записи (один раз, вручную в reg.ru)

- A-запись admin-домена **каждого** узла → IP этого узла (статично, навсегда):
  `admin.example.net → IP1`, `admin2.example.net → IP2`, …
- A-запись `happ.example.com` → IP любого узла для старта (дальше фейловер ведёт сам).

### Узел с Coolify

Coolify сам поднимает прокси на 80/443, свой Caddy не нужен — деплоится только сервис
`app` из `docker-compose.yml`.

1. Создай ресурс **Docker Compose** из репозитория (файл `docker-compose.yml`).
2. В **Environment Variables** задай (см. `.env.example`): `NODE_ID`, `NODE_LABEL`,
   `NODE_PUBLIC_IP`, `NODE_PRIORITY`, **`CLUSTER_URL`** (свой admin-домен), **`PEERS`**
   (admin-домены других узлов), `CLUSTER_SECRET`, `SECRET_KEY`, `ADMIN_USER`, `ADMIN_PASSWORD`.
3. Назначь домены сервису `app`: **свой admin-домен** → порт **8080**, и **каждый домен
   подписок** → порт **8081**. В Coolify домен привязывается к порту, поэтому в поле
   «Domains» пиши с портом: `https://happ.example.com:8081`. Готовую строку «Domains» для
   всех доменов подписок панель показывает в `/settings`.
4. Доп-порты наружу открывать **не нужно** — узлы ходят друг к другу через admin-домен по 443.

### Узлы без Coolify (docker compose + Caddy)

```bash
git clone <репозиторий> sub-cluster && cd sub-cluster
cp .env.example .env      # NODE_ID/NODE_PUBLIC_IP/CLUSTER_URL/ADMIN_DOMAIN/PEERS/секреты
docker compose -f docker-compose.standalone.yml up -d --build
docker compose -f docker-compose.standalone.yml logs -f
```

Caddy терминирует HTTPS для admin-домена узла и доменов подписок (on-demand TLS). Наружу
нужно открыть только **80/443** — отдельные порты кластера не публикуются.

## Настройка reg.ru

1. В аккаунте reg.ru включи **REG.API 2.0** и добавь **публичные IP всех узлов** в белый
   список API. Если домены в разных аккаунтах — IP узлов нужно добавить в **каждый** аккаунт.
2. Убедись, что зона домена подписок (напр. `example.com`) обслуживается в этом аккаунте.
3. Понизь TTL A-записи поддомена (например, 300 c) для быстрого переключения.
4. В панели → `/settings` добавь домен(ы) подписок: зона, поддомен, логин/пароль reg.ru,
   при желании — свой порядок узлов; отметь «домен по умолчанию». Сохрани.

## Как работает фейловер

- Каждые `poll_interval` сек узлы пингуют друг друга (через admin-домены по 443). Узел
  считается мёртвым после `fail_threshold` неудач подряд.
- **Активным** должен быть самый живой узел с наименьшим `priority` (для каждого домена
  подписок — отдельно: домен может задать свой порядок узлов).
- Если активный мёртв — следующий по приоритету живой узел переписывает A-запись **этого
  домена** на себя его аккаунтом reg.ru. Admin-домены статичные и не меняются. Против
  **split-brain** по умолчанию требуется **кворум** (большинство узлов согласны, что
  активный мёртв).
  ⚠️ При **2 узлах кворум недостижим** — для авто-фейловера нужно **≥3 узлов**, либо
  отключи кворум в `/settings`.
- **Failback (preempt):** когда вернётся более приоритетный узел, он забирает DNS обратно
  (можно отключить).
- **Ручное переключение:** в `/cluster` — «Сделать активным (все домены)» переносит DNS
  всех включённых доменов на узел и «пинит» его; «Снять пин» — вернуть авто-режим.

## Панель

- `/` — **графовый редактор подписок**: источники (upstream-подписки) → ноды → маршруты
  (твои публичные пути). Ноды:
  - **Источник** / **Ключ** — входные ссылки (со слиянием и переименованием);
  - **Группа** — корзины-страны, каждая → один xray-конфиг с клиентским балансером `leastPing`;
  - **Авто-выбор** — все входы → один балансер (клиент сам выбирает быстрейший по пингу);
  - **Роутер** — маршрутизация по приложениям: пресеты `geosite`/`geoip` (Telegram, YouTube,
    Discord, WhatsApp, …) → разные таргеты (ссылка / группа / авто-выбор / direct), остальное
    → default. На выходе одна запись с per-app routing.
- `/classic` — то же списком форм.
- `/cluster` — узлы, живость, активный, ручное переключение, журнал, добавление узлов, редеплой.
- `/stats` — обращения устройств к подпискам; устройство можно вручную заблокировать или
  разблокировать. Заблокированному возвращается валидная подписка с единственной заведомо
  нерабочей нодой `Заблокирован`, чтобы клиент удалил прежний список серверов. Полное
  сообщение `Вы были заблокированы. Обратитесь в Telegram @Jammeren2` передаётся в
  заголовке и подписи самой подписки, а не в названии ноды.
  Блокировки синхронизируются по кластеру.
- `/zapret` — диагностика обхода DPI (см. ниже).
- `/settings` — домены подписок (reg.ru per-domain), параметры фейловера.

Один и тот же URL маршрута подходит и для Happ/Xray-клиентов, и для **Koala Clash / Clash
Verge / mihomo**. Формат выбирается по `User-Agent`: существующая выдача Happ (JSON или
Base64) не меняется, а Clash-клиенты получают готовый YAML с `proxies`, группами выбора и
автотестом задержки. Если клиент скрывает свой `User-Agent`, добавь к ссылке
`?format=clash`; вернуть прежний формат явно можно через `?format=happ`.

## zapret (обход DPI) — диагностика на узле

Страница `/zapret` — стратегии обхода DPI + **авто-тест**: меряет, какие из ~20
заблокированных/троттлящихся сервисов (Discord, YouTube, WhatsApp, Instagram, …) доступны
с узла **с обходом и без**, и сам ставит лучшую стратегию (можно сменить). Логи — в модалке
(эфемерные).

Две кнопки набивают список готовыми стратегиями:
- **«+ набор по умолчанию»** — канонические стратегии (`fake,split2`, `fakedsplit`,
  `multisplit`, `syndata`, QUIC-fake для YouTube, комбо TCP+QUIC);
- **«+ комьюнити»** — популярные мульти-секционные рецепты (QUIC google + Discord/STUN по UDP
  + general через `hostfakesplit` и т.п.).

Обе ссылаются на fake-payload'ы из установленного zapret (`/opt/zapret/files/fake/`). Можно
также **вставить свой конфиг zapret целиком**, в т.ч. мульти-секционный через `--new`, с
путями к листам/бинам. Параметры уходят в `nfqws` **списком аргументов (без shell)**; валидация
отсекает только мусор и shell-метасимволы, конкретный белый список флагов не ведётся.

Включается **одной переменной** `ZAPRET=true` в `.env`: она кладёт `nfqws` (release-бинарник
bol-van/zapret, статический — версия в `ARG ZAPRET_VERSION`) в образ **на сборке** и включает
применение стратегий в рантайме; `cap_add: [NET_ADMIN, NET_RAW]` уже прописан в compose.
**Важно:** установка происходит на сборке — после смены `ZAPRET` пересобери:
```bash
# .env:  ZAPRET=true
docker compose up -d --build      # узел скачает release-nfqws (~8 МБ) и положит в образ
```
`ZAPRET=false` (или убрать строку) — zapret не ставится, `/zapret` даёт только baseline.
zapret трогает только egress контейнера, не хост.

> **Если nfqws «не найден» после деплоя** (частый случай с Coolify/Nixpacks, когда наш
> Dockerfile не выполняется): при `ZAPRET=true` узел **сам докачает nfqws и xray на старте**
> с GitHub (release-файлы, проверка по sha256) в `/opt` (или `/data`). Это происходит в фоне —
> обнови `/zapret` через ~минуту. Перебилдить образ при этом не обязательно, достаточно, чтобы
> в рантайме был задан `ZAPRET=true` и контейнер перезапустился.

Роутер-нода умеет два режима: **клиентский** (отдаёт xray-конфиг, разруливает сам клиент) и
**серверный (gateway)** — см. ниже.

## Узел-gateway (универсальная ссылка)

Серверный режим роутер-ноды: узел поднимает **один VLESS-ws inbound** (xray-core) и
раскидывает трафик **на самом узле**:

```
клиент → vless+ws+tls (домен:443, путь /vlessws) → xray на узле → routing:
   • YouTube/geosite → freedom 'direct' (egress, помечен fwmark) → nfqws DPI-обход
   • остальное       → balancer leastPing(аплинки) → лучший VPN-ключ
```

Включение: в редакторе у роутер-ноды раскрой **«⚙ Серверный режим (gateway)»**, поставь
галочку, (опц.) задай домен ссылки, сохрани граф — кнопка «Получить ссылку» покажет
**универсальную `vless://`**. Подключи к роутеру входы: zapret-таргет (правило → `direct`),
авто-выбор (аплинки), и т.д. Можно подать на вход роутера/авто-выбора и **ноду-маршрут**.

Требует образ с `ZAPRET=true` (ставит xray-core + nfqws + geoip/geosite) и `cap_add`
NET_ADMIN/NET_RAW (уже в compose). TLS терминирует Caddy/Coolify на 443; путь `/vlessws`
проксируется на порт **8084** (Caddy-вариант делает это сам; в Coolify направь путь вручную).
zapret-обход применяется только к freedom-трафику (по fwmark) — соединения с аплинками не
затрагиваются.

## Безопасность

- **Секреты — только из окружения/панели.** В коде нет доменов, IP, токенов, HWID.
  `.env`, `*.db`, `config.json` — в `.gitignore`.
- Перед запуском задай **сильный** `ADMIN_PASSWORD` (пустой/дефолтный → отказ старта),
  уникальные `SECRET_KEY` и `CLUSTER_SECRET` (одинаковые на всех узлах).
- Пароли reg.ru и redeploy-токены хранятся в БД **зашифрованными** (`SECRET_KEY`).
- Peer-API между узлами подписан **HMAC** (`CLUSTER_SECRET`); действия из UI — сессия + CSRF.
- Панель/подписки рассчитаны на работу **за HTTPS-реверс-прокси** (Coolify/Caddy).
- Compose по умолчанию даёт контейнеру `cap_add: [NET_ADMIN, NET_RAW]` (для zapret/NFQUEUE).
  Не используешь обход DPI — поставь `ZAPRET=false` в `.env` и убери `cap_add` из compose.

## Редеплой узлов из панели

На вкладке `/cluster` у каждого узла есть кнопка **«Редеплой»** (если задан вебхук).
Приложение ничего не пересобирает само (в контейнере нет git/docker) — оно дёргает
redeploy-вебхук узла.

- **Coolify:** в «redeploy-вебхук» вставь deploy-webhook из Coolify, в «redeploy-токен» —
  API-токен (уйдёт как `Authorization: Bearer`).
- **Без Coolify:** на ХОСТЕ запусти агент `redeploy-agent.py` (делает `git pull && docker
  compose -f docker-compose.standalone.yml up -d --build`):
  ```bash
  REDEPLOY_TOKEN='секрет' REPO_DIR=/root/sub-cluster \
    python3 redeploy-agent.py    # слушает 0.0.0.0:9090 (закрой порт фаерволом)
  ```
  В панели: redeploy-вебхук = `http://host.docker.internal:9090/redeploy`,
  redeploy-токен = тот же `REDEPLOY_TOKEN`.

## Совместимость

Режимы подписок: **зеркало** (один upstream как есть) и **слияние** (несколько → один
base64-список с агрегацией трафика). Легаси-зеркало можно создать при первом старте, задав
`UPSTREAM_URL` + `SUB_PATH`. Здоровье узла: `GET /healthz` на любом порту → `ok`.
